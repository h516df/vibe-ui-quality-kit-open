# 云端项目工作流 0.5.7

## 起点

按 [许愿式闭环](INTAKE.md#许愿式默认闭环) 对原需求成品结果负责：用户表达目标和评价，Agent自行选择实施过程并持续到授权范围内的交付。当前主要场景是手机App，围绕原App的实际界面与完整操作验证；样例、流程和检查只服务于目标。常规步骤按实际任务裁剪，相关规则按缺口读取，普通技术选择不交给用户逐项决定。

本目录为跨项目通用入口。[CORE.md](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/CORE.md) 的同版简约规则保存到每个项目默认分支的 AGENTS；不以跨私有仓库读取成功作为开始工作的前提。代理按任务核对相关 PR 和对应分支交接，新项目建仓时接入；详见 [采用状态](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/REPOSITORIES.md)。

用户已明确要求：这套流程默认由代理处理，不要求用户逐项目提醒、复制启动语或执行接入命令。规则已知且目标项目获授权时，自动采用适用步骤；沿用已有接入，必要澄清集中处理。跨会话自动生效以实际加载的项目/全局指令为准，不能把私有 GitHub 存档称为账户级配置。

从当前目标、写手和有效成果接续，只读取本次相关项目规则与交接，缺信息再定向补读。核对远端默认分支、进行中分支、PR 与未提交改动，接续已有成果。用户当前指令优先；不得因通用模板增加与任务无关的审批或覆盖项目约定。源码与重测试优先已授权云端环境；确需本机的部分沿已有授权通道由本地 Codex/DSH 处理，不自动迁移私钥、私人资料或生产登录态。

## 执行效率纠偏（2026-10-29）

以下是已有流程的执行约束，不是新增项目、检查工具或审批环节。用户反馈开发太慢时，要先改变本次实际工作路径；只提交流程文字不算效率改进完成。

1. **一次定位，增量接续。** 一次性读取当前 main SHA、相关在办 PR、最新 Release 与 HANDOFF 顶部摘要；事实冲突以实时远端和实际产物为准。已知有效的源码、研究、测试和授权直接复用；只针对缺口补读，不把整个历史重新检查一遍。发现交接把已发布版本写成待发布时，在所属任务收尾修正，避免下一写手重复调查。
2. **先给可运行的主路径。** 对已授权开发/修复，先选一个最影响使用的完整场景，优先沿现有代码和任务分支形成可操作改动；必要设计预览尽早给出。没有影响该场景的证据，不新建第二套架构、Agent、脚本、长报告或跨项目整理。数据、权限、签名高风险仍先做必要保护。
3. **分层验证，保留强制门禁。** 每次改动先运行相关的廉价检查与目标交互；未改变部分复用有效证据。正式候选按仓库保护和发布规则跑完整 CI、安装升级及发布核验；不要把每个中间小修都当成新发行。CI 在等待时可继续不冲突的工作，但不得把 pending 写成通过。
4. **等待释放主控时间片。** 遇到 PR/CI、网络、设备或独立 Agent 的结果尚未返回时，先保留原任务入口、精确提交 SHA（如适用）、run/job/任务 ID、等待条件及下次合理检查时机；由已启动的异步工作继续等待，主控转去处理**已授权、无写入冲突、可以独立验收**的现有任务，允许跨项目切换。恢复时先读回原结果和副作用，再按失败修复、整合或交付接续；不忙轮询、不重复触发构建/发布、不因切换丢失原任务。云端独立读取/验证可受控并行，低配本机原则上只跑一个重任务；同一文件、分支、设备状态与整合入口仍串行。没有合适的独立任务就正常等待或收尾，不为并行新造工作。跨会话没有持久调度能力时，必须说明待回收入口，不能声称后台会自动接续。
5. **失败不盲重试。** 先核实原任务 ID、错误、当前远端状态与可能副作用，再修复具体原因并复测相关范围；回执不明先只读查结果。避免重复触发发布、重复上传、重建分支或让用户转述日志。
6. **用实际产出检验。** 收尾只报告可用入口、用户场景是否通过、未验限制与必要下一步；能从任务/CI观察到时，记录首次可运行结果、完整交付耗时、无效重试和同问题返工，不编造数字。下一次同类任务应减少重复操作；若没有变快，分析实际耗时而不是继续堆规则。

**当前成品目标与设计偏好。** 用户希望自然语言提出需求，由代理负责直到自己的 GitHub 开源仓库有可下载使用的成品。对任务中已明确的“开源、下载使用”，把源码、许可证、正式 Release、对应安装包、下载核验和更新保数据纳入完成条件，沿现有授权持续收尾，不在完成代码后另问是否打包发布。已有私有项目不因此批量转公开；发布前沿隐私扫描、许可和原签名规则处理，必要的本人授权仍保留。苹果产品的精致统一，与优秀开源软件的清爽实用，是当前两种默认视觉参考；按用途选一套，真实查看对应参考与最终画面，不把“开源”当单一皮肤或混搭控件。用户只需表达目标、偏好和体验，代理承担技术调度与首轮排错。

**完成须分清三件事：**主要用途在最终产物上可操作并按风险检查保存重开/错误恢复；真实界面、中文、小屏及相关大字状态经过查看，实质视觉改版按需由未参与实现者复核；GitHub 发行、附件与访问条件实际读回，必要时下载核对摘要。沿现有 [DELIVERY](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/DELIVERY.md) 和检查/发布工具执行，用户无需填写验收表。构建、流程更新、脚本自检或发布元数据不能证明全部可用；目标设备或安装升级未实际访问就标未验，不凭文件更新宣称所有云端会话已加载或任意需求可以无人介入交付。

## 1．区分讨论、收集与实施

代理根据自然语言和当前阶段判断，不要求固定口令，也不把每个新任务强制放进等待队列。

- 用户明确要求开发新项目、修改、修复或继续实施：整理简短范围后直接执行，不再询问是否开工。
- 用户说先讨论、先记下或候选想法：更新需求池，不据此实施。用户已选择频繁网页试用时，当前体验反馈默认接续实施并更新同一预览，除非明确只记录或暂停；存在歧义时先记录可确认部分，只集中澄清会改变主要含义的内容。
- 对当前任务计算口径、数据含义或本批错误的纠正及时纳入。独立新增功能默认进入下一批候选；不把澄清和缺陷一律推迟。当前用户的暂停、收集或立即处理指令优先。

由代理保留用户原话、场景、期望效果和状态，自己的推测单列；候选不是实现承诺。只保留一份需求状态，PR、TASK 和 HANDOFF 用链接引用。细则见 [需求与批次](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/INTAKE.md)。

每批围绕一个相关体验或明确结果，代理写明例子、2–5 条完成条件、当前边界和重要依赖。按价值与风险建议顺序，避免把全部积压变成大版本；用户无需打分、填表或管理排期。批内分步实现并检查，网页试用可反复更新同一入口；不要把“一次交付”误解为只能一个提交、一个 PR 或等全部项目功能完成。

新项目先查当前环境与账号能力，路线见 [云端能力与建仓](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/CLOUD_CAPABILITIES.md)。不能在收到明确实施请求后，只记一条待办便结束。

### 网页持续试用与已明确的成品交付

本批先固定已经明确的要求与不做项，优先做代表界面的快速预览，让主要方向尽早可见；主动查找相关网上/GitHub 参考，已有有效证据则复用，新增问题定向补查。网页持续试用中的反馈默认及时接续，连续到来的相关要求合并处理；实施中的纠正并入当前批，不为每句话重启调研、重做、全量测试、部署和长交接。无需固定口令或新增审批。

视觉方向未稳定前，不围绕旧假设补齐所有页面和完整适配。预览仍先完成语法、启动与关键操作检查，数据/权限安全不降低。试用阶段完成可测试调整就及时更新同一入口，不等待凑批或最终满意。内部没有用户可见变化时才避免反复部署。用户明确要求 GitHub Release（含预发行）/APK 等正式发行，或任务已明确以开源可下载成品为目标后，由代理持续完成相应验收与发行，沿用已有授权；预览更新不需要逐轮发行确认。具体例子与阶段判定见 [INTAKE](INTAKE.md#反馈迭代节奏)。

### 把需求落实到实际结果

沿原 TASK/Issue 逐项关联“用户要完成的事 → 输入与操作 → 预期结果 → 实际结果及证据”。小修可只写一行，不另造验收系统或要求用户填表。完成条件检查用户可观察行为，不能用文件、按钮存在、接口返回成功或测试数量替代。例如“收藏后退出重开仍能找到原内容”，不能缩成“收藏按钮可点击”；“离线可用”不能用在线演示和伪数据证明。已确定的离线、隐私、无密钥使用、导出和保数据等约束纳入对应场景，不擅增新功能。

先打通目标平台上一条完整代表路径，再扩展：从真实入口开始，使用长度、数量和状态接近日常情况的合成内容，走到结果落地及相关返回/重开。演示占位、未接通的控件、静默兜底不能算完成；提前区分产品缺陷与环境阻塞。首个切片用于尽早发现方向错误，仍须完成本批其余约定。

界面改版先在代表页面检验已选设计语言，把参考转成具体决策：内容主次、字号、密度、组件、导航和反馈。查看同内容/视口的实际渲染，操作主要流程，先修影响可读性、发现入口、触控和布局的缺陷，再打磨对齐、间距、图标和动效。按影响检查小屏、大字及相关空白/加载/失败状态；已有设计不每次重做选型，不以主观评分代替用户审美认可。

收尾回看本批原需求和最新纠正：每个完成条件注明 passed / failed / not run、当前来源/产物和最小证据入口。未满足项保留在原记录，说明能否继续由代理解决；阻断核心用途、数据正确性或已约定交付的缺陷继续修复，不能以“后续优化”结案。其他限制按影响如实披露，不把无关未来风险加入门禁。纠正仅使相关旧证据失效，复用有效结果，禁止为了通过而删除断言或降低既定要求。

### 交付阻塞优先的单轮闭环

每轮先判断**离用户真正能用还差什么**，把开发活动围绕当前最靠前的阻塞组织。此处是执行顺序，不新增审批、需求表或第二套队列。

1. **恢复现场**：从原任务和现有 PR/Release 找到最近可运行的版本、已验证场景及失败证据；用一句话写清用户本轮要成功做成的事。旧结果有效则复用，不能只凭历史交接推断仍然有效。
2. **只选当前关键阻塞**：优先修无法打开、数据错误或丢失、主操作不通，再处理明显体验割裂，最后做装饰性优化。一个任务默认一个结果负责人、一个当前产品切片；仅当工作独立、不冲突且能缩短交付时间时并行。不得因新想法打断已有关键路径。
3. **尽快取得可操作证据**：先让一条代表用户路径在目标环境或最接近的可用环境完整跑通（进入→操作→保存或反馈→返回/重开），再扩展其他页面与边界。首轮失败先修关键路径，不靠增加功能数量或测试数量掩盖。
4. **一次失败，一条修复链**：保留原报错、源码/版本与复现输入，定位根因后做最小修复、定向复测；变更影响之外的有效检查不重跑。同类失败连续两次仍未解决时停止补丁式试错，复核假设与执行环境；副作用不明先查原任务与远端，不重复提交、签名或发布。
5. **按完成条件收尾**：所有本批核心用户场景与已授权交付渠道通过即交付，不为无关检查拖延；未通过则明确当前阻塞和可独立继续的工作，不把“已写代码/CI绿/已发版”称为“好用”。最简回执只给可用入口、实际验收、剩余限制和确需本人做的一步。

衡量流程有没有变快，观察同一需求从接手到**第一条真实可操作路径**、到**最终可用产物**的时间，以及重复修复/重复构建次数；不拿行数、PR数、代理数或规则长度当生产力。只在原任务/PR记录必要数据，不新建报表系统。

## 2．先复用，再实现

任务开始与关键方案选择时，先检查项目已有实现和研究，再主动寻找网上、GitHub、官方文档和成熟产品中的可复用方案；覆盖产品流程、视觉/交互、技术实现、故障定位和测试方法。实际阅读相关文档/源码/issue，体验任务所需的演示，比较后说明采用与舍弃理由。不能只凭记忆、搜索标题、截图或 star 数决定，也不等用户再提醒才查。已有证据仍适用时直接沿用，小改或新问题定向补查，不反复进行整套调研。细则见 [主动研究与复用](RESEARCH.md)。用户体验保持少步骤，常用路径少必填项，次要信息按需展开。

视觉任务先确定字体、字阶、间距、材质、圆角、图标、菜单、导航、动效、暗色/减少动态效果。已有设计系统则复用。不要求用户逐组件审批；显著改变方向时先展示代表页面。外观检查包括空状态、错误、加载、长文字和小屏，不能只看默认静态画面。动效在实际运行中核对，必要时提供短录屏；检查快速连续操作、中途切换和减少动态效果。截图通过不能证明动画自然。

新产品、明显改版或“不好看”按[当前两种审美方向](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/STYLE.md)先选贴合用途的构图、内容密度和控件主次；局部小修继承已有设计。复杂接续由代理使用现有 resume 同时核对源码、相关PR与最近正式发行候选，继续读需求和交接决定下一步；发行链接及摘要只是元数据，不代表已下载、安装、签名或设备验收，用户无需自己找分支和下载入口。

## 3．一份主要源码，小步实现

以指定 GitHub 仓库及任务分支为长期源码依据。顺序接力只在前一写手已停止并移交后沿用分支。不同活跃会话各用独立分支、独立工作区及唯一会话标识；同批可关联多个小 PR，不因此增加用户查看版本的次数。变更同时更新必要说明，不重写无关历史。

优先修改已有实现，避免通过 v3/v4/v5 不断覆盖同名逻辑。发现结构债务时只整理当前任务需要的范围，先保证数据兼容，不顺带重写整个项目。

预览、检查和发布应追溯到相同源码内容。平台必须使用第二个托管源码库时，记录来源 SHA、平台 SHA、产物校验/比对和部署 ID，不能把两个仓库的 SHA 写成相同。传输失败先检查参数、大小和响应格式，不盲目重复整份上传。

多 Codex 并行或接力先执行 [MULTI_CODEX](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/MULTI_CODEX.md)：从项目专用协调分支原子领取任务、分支与路径范围，写入前核对代次与租期。暂停/到期保留占用和原成果，移交明确前一写手已停；不把 issue 描述当互斥锁。一个登记的整合者合并同批就绪成员、核对最新成员提交，在整合后的源码上验证，统一发布。普通工作会话维护各自 PR 或 docs/tasks/<task-id>.md，公共 HANDOFF 与需求池由整合者汇总，减少共享文档冲突。

## 4．按风险检查，保留证据

讨论已形成可实施共识时，代理说明结果后直接推进，不等额外开工口令。默认一个主写手完成实现和针对性自检；低风险小改不自动开审查 Agent。独立复核用于数据迁移、权限、签名/发布逻辑、跨模块协议或明显视觉改版等实际风险。

冒烟只确认启动、连接或进入页面；相关入口未变且已有有效结果就复用，不每个小步骤重复启动、冒烟和全量回归。本次用户可观察结果及相关必跑项通过、无未解风险后即交付；只有新改动、具体失败或证据缺口才继续检查。不要为检查而增造夹具、旁支功能和第二套验证入口。

防御代码放在实际外部输入、持久化、网络和权限边界，内部沿已明确的类型和接口契约实现；无真实失败场景或兼容需求，不层层判空、堆兜底和备用引擎，不吞异常或静默降级伪造成功。

按用户自2026-10-25转为Plus的有限额度执行，复用上下文和有效结果；本地、云端Codex共用套餐额度，DSH保留按需协作，不擅改用户指定模型/档位或购买额度。限额前保存可接续进度；未验证调度通道不声称自动续跑。Actions、Codex Cloud、模型限额和本机环境分别诊断，某项受阻不推断其他通道全部不可用；平台明确拒绝不能换工具重放同一动作。

- quick：语法、配置、必要的静态检查；文案/颜色等轻改通常只需相关检查和目标画面。
- core：涉及金额、状态保存、导入、迁移、权限或主要交互时，运行相应计算与浏览器用例。稳定环境执行关键页面截图比较；截图不能判断审美是否合意。
- 扩展：只有跨模块变更、失败或剩余风险才扩大范围。一次相关检查通过后停止重复运行；新改动仅复查影响范围。样式/布局先查目标画面及主操作，不重新跑未变模块的全套构建；金额/保存等变化查相应回归，项目强制检查不省略。可复用证据须说明受检内容与当前内容相同，不能把旧提交通过直接改名为本轮通过。失败先定位，再重跑相关项。

计算测试覆盖用户例子和有意义的边界；浏览器用例尽量通过可见文字/角色操作，数据相互隔离，使用自动等待而不是固定睡眠。依赖锁定、日期固定、截图同环境。失败时记录截图/trace；不要默认保存真实账单或凭据。

每项标注 passed / failed / not run、执行命令、日期、来源提交。干净提交上运行的结果绑定该提交；若在工作树验证，注明基线+文件状态，提交后核对内容。旧会话通过不等于当前通过。未配置的检查、守卫脚本、演示数据、模拟器和真机的能力要分别说明。

修复验收引用旧报告时，先检查原始截图/trace等证据确实存在、属于该报告且与记录摘要一致，并能对应到原失败场景。缺失、被改动或无法关联的证据不能支持“同一断言修复前后通过”；可以重新建立已知坏版本证据，或据实报告比较未证实，不能编造旧报告。此处采用 [gstack 的修复前后证据核对](https://github.com/garrytan/gstack/blob/6f7488a70f23bc71745bde704eda98033cc33bfa/qa/sections/browser-verify.md) 思路，沿现有浏览器/原生检查工具实施；文件完整性不证明内容真实、需求已全部覆盖或审美已被用户认可。

## 5．自动化稳定动作，按授权发布

交付的完成条件、构建/鉴权故障定位、正式发行状态和原生附件的可执行核验见 [DELIVERY](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/DELIVERY.md)。用户指定的渠道与发行级别必须进入本批完成条件；未测限制如实披露，不擅自扩成用户未要求的发布阻止条件。构建成功、链接可见和正式交付分别验证。

文档整理可按风险省略无关业务构建；使用 skip-ci 标记前核对保护要求，不能跳过分支保护要求的检查或伪造成功状态。若必须检查，使用现有流水线验证原提交，合并相同源码时避免重复触发无关构建。

先跑已确定的廉价检查，再运行必要功能检查；CI 同分支新提交取消过时的检查任务。限制超时、依赖安装次数及失败附件保留期。不默认引入多代理、定时任务、收费后端或新平台。

修改 GitHub Actions 时使用固定版本的工作流语义校验（例如 actionlint），检查表达式上下文和字段；单纯 YAML 解析不能替代。

源码先提交并推送，再从该提交打包。使用现有发布工具和访问范围；已有授权内推进，保留私有权限。没有授权的公开发布、不可逆动作或对外发送另行处理。发布工具成功后记录 URL、源码提交和部署标识；检查非终态直到明确结果。不能把已保存版本称为已上线。

通用检查工具不负责管理平台密钥或直接部署；各项目通过原有官方接口适配。不要把敏感输出写入交接或附件。PR 自动检查不授予默认写权限，不用 pull_request_target 执行不可信代码。

## 6．交付与接续

需求池分别记录候选、待做、开发中、已验证和已发布，阻塞与证据另列。检查通过、源码保存、部署成功和实体设备验收不能混为“完成”。只更新本批条目；长期需求池保持打开，不用关闭关键词把整池自动关闭。

发布前保留上版来源提交、产物/部署标识及恢复说明。涉及持久化格式变化先明确备份、迁移和恢复路径并验证；保留旧 APK 不代表 Android 支持直接降级。安卓项目按需采用 [交付验收模板](https://github.com/h516df/vibe-ui-quality-kit-open/blob/main/workflow/templates/ANDROID_DELIVERY.md)，不把模板当作已接通。


单会话直接维护交接；多会话按登记角色先保留各自任务记录，整合者更新现有 HANDOFF 顶部简短当前摘要，历史保留在下方或独立归档并链接，不每次复制整份聊天。长期偏好写 AGENTS；当前任务进度留任务/交接文档，避免不断复制一整套说明。模板变更记录版本与目标项目采用的提交。

把源码、检查配置和交接一起提交推送，核对远端分支 SHA。新任务建立 PR，同一目标修正优先续当前任务/PR，不为中间失败反复新建发布批次；遵守协调协议，不回写冻结成员，不擅自合并其他任务。CI 实际完成前标 pending/not run，失败说明具体原因。最终先给实际结果、可用入口、剩余限制与必须本人做的最小一步，再按需链接仓库/分支/PR/准确提交和检查证据。接续信息由代理保存并主动恢复，不要求用户搬运提示词。

用户集中判断“是否符合生活方式、是否舒服”，代理承担功能核对、错误定位、备份和发布工作；必须人工完成的设备授权或真机反馈，说明原因并压缩到必要步骤。
