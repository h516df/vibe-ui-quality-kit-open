# 需求收集与集中交付

规则版本 0.5.5 · 2026-10-23。由代理维护，用户只需自然表达想法与目标；沿用项目已有需求池，不引入额外平台或填写流程。

## 许愿式默认闭环

- **代理整理需求并推进。** 从用户原话、场景和最近纠正恢复目标，用易懂的一句话说明要得到什么，自行整理必要的可观察完成条件。分清用户决定、代理推荐默认和未决问题；可回退的普通默认说明后继续，只有会改变核心用途、数据含义、必要授权或必须本人操作的缺口才集中澄清。用户说“你决定／不懂／很累”时减少技术追问，不要求填规格、选技术栈或管理排期。
- **一个负责人跟到结果。** 沿现有写手、需求池与协调登记核对结果负责人，由其组织实现、处理冲突、收回成果并验收。云端 Codex、本地 Codex 和 DSH 可以按实际能力参与，同项目共用目标和状态，执行者保留独立分支/工作区；跨会话派发仍沿对应授权，不新建控制平台，不虚构已派发或已接入。
- **换入口主动接续。** 从需求池、相关 PR/分支、当前源码/产物和交接恢复最新成果、剩余问题及下一步，不让用户找链接或重讲背景。旧记录只作线索，发现本任务记录与实际结果不一致时，在授权内核对并更正；不因 PR 未关闭就判定功能缺失，不因缺登记就抢占旧写手。
- **先把原用途做完整。** 复用现有成果，先解决阻断本次用途的问题，沿同一预览或安装产物迭代。当前场景的纠正继续处理，独立新想法另记；不擅加功能、重做架构或将协调工具建设当产品进展。代表路径尽早可操作，但不能替代全部约定目标。
- **自检后交用户体验。** 代理先复现并操作相关路径，查看真实渲染，按风险验证保存重开、错误恢复与回归。在已授权实施中，“还是不对／不好用”保留为未解决问题，先核对实际版本和原场景再修复；不要求用户充当首轮测试员，不用构建、截图或发行状态结案。审美认可和不可替代的设备操作由用户反馈，目标环境不可访问时据实标未验。
- **负责人收尾。** 保持现有需求/交接的当前状态准确，先说明实际结果、可用入口、剩余限制及本人必须做的最小一步，技术证据按需链接。用户无需追问哪版能用、是否还需继续，也不需要在执行者之间搬运提示词。规则更新、任务受理与实际使用改善分别报告。

**当前成品目标与设计偏好。** 用户希望自然语言提出需求，由代理负责直到自己的 GitHub 开源仓库有可下载使用的成品。对任务中已明确的“开源、下载使用”，把源码、许可证、正式 Release、对应安装包、下载核验和更新保数据纳入完成条件，沿现有授权持续收尾，不在完成代码后另问是否打包发布。已有私有项目不因此批量转公开；发布前沿隐私扫描、许可和原签名规则处理，必要的本人授权仍保留。苹果产品的精致统一，与优秀开源软件的清爽实用，是当前两种默认视觉参考；按用途选一套，真实查看对应参考与最终画面，不把“开源”当单一皮肤或混搭控件。用户只需表达目标、偏好和体验，代理承担技术调度与首轮排错。

以上默认不改变用户明确的讨论、暂停、发布、权限或指定模型边界，也不代表旧会话或未接入项目已经读取新版。

## 什么情况下开始做

用户明确要求开发、修复或继续实施时直接推进；先讨论、先记录和独立候选想法先收集。已授权的持续网页试用中，当前体验反馈默认接续调整并更新预览。判断结合当前任务与用户原意，没有固定口令，不额外要求一次开工确认。实施请求不能只保存成待办便结束；讨论也不能被当成授权改产品。

“月底剩余只算当月工资”若纠正当前实现口径，应及时修正本批；“以后再加一套主题”属于新想法，进入候选。若用户暂停，按暂停指令处理。只有关键含义不清才集中澄清，其余先自行核对项目。

## 先区分网页试用与正式发行

用户选择反复试网页、边使用边调整时，进入持续试用阶段：当前体验反馈就是继续调整预览的依据，默认及时接续、完成必要检查并更新同一链接，不要求每轮再说“开始”，也不等凑够反馈才更新。连续到来的相关要求并入当前工作；用户明确说只记录/先收集/暂停时才停止实施。独立未来想法仍可留候选。

网页试用部署可以频繁发生，每轮只做受影响的检查和简短交接；不能因为“集中交付”限制用户反复测试。用户明确要求正式发布，或任务已经明确以开源可下载成品为目标时，由代理按既有发行验收完成 GitHub Release（含预发行）/APK 发布；不重复索要同一授权，不把网页满意按钮、源码备份或预览部署当作发行同意。记录预览 URL/部署状态和正式发行状态，避免只写含义不清的“已发布”。

## 反馈迭代节奏

1. **固定已知要求。** 在现有任务/需求池用几行保存目标、主体验、明确约束和不做项；后续沿用，不每句重新猜。新纠正替换冲突假设，未受影响要求保留。用户无需重复说明已选方向。
2. **先暴露方向问题。** 任务开始与关键方案选择时，主动查网上、GitHub 和成熟产品，实际查看资料/操作相关演示，确定采用理由；已有有效研究沿用，新增问题定向补查。新界面方向不确定时，再做一个代表场景的快速预览。复用当前预览入口，避免在核心方向未稳时堆完整功能、全部适配与长文档。快速预览标明未完成范围，不冒充已验收成品。
3. **反馈接续调整。** 频繁网页试用模式下，当前体验反馈默认实施并更新预览；连续反馈合并吸收，不重新走一遍完整发行流程。停止依赖旧假设的重工作，独立工作可继续；仅关键含义不清时集中澄清，不要求固定口令、逐组件批准或额外开工确认。
4. **按改动检查，及时更新预览。** 样式布局检查目标页面/视口与主操作；金额、保存、迁移、权限或核心交互变化运行相应用例。记录与当前源码匹配的结果，未变模块不重复构建。通过后仅因新变化、失败或剩余疑点复查，项目强制检查照常执行。
5. **减少重复收尾。** 完成可测试的调整就更新原预览链接，不等最终满意才更新。仅没有用户可见变化的内部试改不反复部署；不每次重建站点、重做完整发行或写长报告。平台要求的源码保存/私有预览部署验证仍完整执行。同一批复用 PR、任务与站点；交接保留简短当前状态和证据链接，不重复抄整份聊天、旧测试清单或新建一套流程。

可操作预览对外展示前先通过必要的语法、页面启动和关键操作检查；涉及数据写入仍要满足相应安全验证。快速意味着优先验证主要体验，不降低数据、权限、签名或发行标准。预览阶段不是新的发布授权；用户既有确认要求继续有效。

例子：

- 用户已明确要频繁试网页，依次反馈「文字太多」「需要音效」「界面要铺满」：每轮接续调整并及时给出原预览链接，工作中到来的反馈一起吸收；不要求另说开工，不因为尚未满意而停止更新，也不自动发行 GitHub 版本。
- 已经在做全屏界面时补充「不要复古」：修正本批视觉约束，复用菜单、数据和入口；先看代表主屏，不连带重写存档或重复跑未变 Android 构建。
- 调整标题间距只检查相关画面；改工资公式或记餐持久化则运行相应逻辑/保存回归。源码变更影响哪些证据就更新哪些，不把旧通过当新结果。

## 一条需求记什么

- 稳定编号；用户原话和反馈日期。
- 场景与期望；尚不明确的内容标待定位，代理建议/假设另标。
- 状态：候选 / 待做 / 开发中 / 已验证 / 已发布；所属批次按需要添加。
- 阻塞及证据链接单独记录；被撤销或替代的条目保留理由，不默默删除历史。

相同问题合并并保留有价值原话。无需为每句反馈创建独立 issue；一个池中的条目足够时继续使用。复杂需求真正进入批次后才按需要拆分，不增加用户管理负担。模板见 [BACKLOG](templates/BACKLOG.md)。

## 一批怎样交付

代理从相互关联的问题中整理一个可完成的结果，注明完成条件、范围与重要依赖；优先处理金额/数据错误、阻断操作和减少步骤。用户可以调整顺序，但不必逐项评分或批准技术方案。

批次启动后专注当前结果；新增独立想法先入池，本批口径纠正与实际缺陷及时处理。内部可有多个提交、相关检查和小 PR，试用阶段可多次更新同一预览，正式发行在用户明确要求后集中完成。若确需中途让用户判断方向，只展示有决定价值的代表体验。

源码保存、云端测试通过、真实设备通过和公开/私有发布分别记证据。不因 CI 没启动而盲目重试，不把工作区通过冒充 Actions 通过。完成后仅更新本批条目并关联 PR/提交/部署，不关闭整个长期需求池，也不把所有历史条目重复拷入 HANDOFF。

## 新 Codex 云端任务

项目 AGENTS 必须链接需求池与当前交接入口。代理先核对远端、相关 PR、对应分支交接与池中状态，再判断本次是讨论、收集还是实施。项目未指定需求池时由代理在获授权仓库建立并加入入口；新建项目时接入简版。GitHub issue 和仓库文件并非 ChatGPT/Codex 账户级指令。
